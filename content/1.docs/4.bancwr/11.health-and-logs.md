## The health indicator

Every page shows the bunker's health at the top left, next to the page title. Every role can see it.

| Indicator | Meaning |
|-----------|---------|
| **Healthy** (green) | Every check passes. |
| **Degraded** (yellow) | At least one check needs attention, and none is failing. |
| **Down** (red) | At least one check is failing, or the bunker did not answer. |
| **Checking…** (grey) | No answer yet. |

Click the indicator to see each check and its detail, and when it was last checked. Click **Check now** to check again straight away. Otherwise Bancwr checks every 30 seconds while the page is open.

The **Dashboard** shows the same checks under **Bunker Status**, with the bunker's public key.

![The Dashboard, with the Bunker Status card showing all four checks as OK](/img/screenshots/bancwr/status.png)

## The four checks

Each check shows **OK**, **Needs attention**, **Failing** or **Off**.

| Check | OK | Needs attention | Failing |
|-------|----|-----------------|---------|
| **Signer** | The bunker signs and verifies a test event. The event is never published. | | The bunker could not sign, for example because it is locked. |
| **Database** | The database answers. | | The database did not answer. |
| **Relays** | Every NIP-46 relay is connected. | Some relays are connected, not all. | No relay is connected, or NIP-46 is on with no relays set. |
| **Administrator** | An administrator is registered. | No administrator is registered, so nobody can manage the bunker. | The team could not be read. |

The **Relays** check lists each relay and whether it is connected. A relay that is still connecting counts as not connected, so the check reads red for the first few seconds after the bunker starts.

When NIP-46 is turned off, the **Relays** check shows **Off** and does not count towards the overall health.

If the bunker does not answer at all, the indicator shows **Down** with a single **Bunker** check. The bunker may be stopped, or the console cannot reach it.

The details never include raw errors, file paths or keys. For the full error, read the bunker's log on the server:

```bash
podman logs bancwr-bunker
```

### When the Signer check fails

If the bunker cannot unlock its key, it keeps running so it can say why. The **Signer** check is red with the reason, NIP-46 does not start, and every page except the dashboard's health answers with an error. See [When the bunker will not sign](/docs/bancwr/protecting-the-key#when-the-bunker-will-not-sign).

### Health checks for containers

The health indicator is a report, not a probe. Compose uses a separate check, `bunker healthcheck`, which asks the bunker's `/health` endpoint whether it is running. A relay going up and down never restarts the container. See [Check it is running](/docs/bancwr/installation#_10-check-it-is-running).

## The dashboard

What the **Dashboard** shows depends on your role.

### For administrators

- The bunker's metrics, counted since the bunker started:
  - **Total Signatures**
  - **NIP-46 Connections**: apps connected now.
  - **HTTP Requests**: requests the bunker's API has answered.
  - **Requests refused (rate limit)**: requests refused because a connection went over its rate limit. See [Rate limits](/docs/bancwr/connecting-apps#rate-limits).
  - **Waiting for approval**: requests waiting under **Approvals**. See [Approval before signing](/docs/bancwr/approval-before-signing).
- **Bunker Status**, with the four checks.
- **Recent Activity**: the latest signatures, with **View All** linking to the full log.

### For signers

- **Bunker Status**.
- **Your Connected Apps**: the apps connected for you.
- **Your Recent Signatures**: what the bunker signed through your apps.

### For viewers

- **Bunker Status**.
- **View the team**, a link to the team list.

## The running version

The sidebar header shows the version under the name, as `V 0.1.0`. This is the bunker's version. The bunker and the console are released together under one version, so the console shows one.

When the sidebar is collapsed, the name and version move into a tooltip on the logo.

To check that both containers run the same version, compare them on the server:

```bash
podman logs bancwr-bunker 2>&1 | grep -m1 'starting'
curl -s http://127.0.0.1:3001/api/version
```

The bunker's first log line carries its version, such as `Bancwr Diogel 0.1.0 starting...`. If the two differ, the containers were not updated together. See [Updating](/docs/bancwr/updating).

`0.0.0` means a build without a version, such as one built from source by hand.

## The Logs page

The **Logs** page shows the **Signing Activity Log**. Only administrators can open it.

It lists the bunker's signatures, the newest 100 first. Click **Load older** for the rest. Only successful signatures are listed.

| Column | Shows |
|--------|-------|
| **Timestamp** | When the event was signed. |
| **Event Kind** | The kind of event signed. |
| **Member** | The team member the app's connection was made for. |
| **Signed as** | The identity that signed. Shown only when the bunker holds more than one. |
| **App** | The key of the app that asked for the signature. |

If the member has since been removed, the **Member** column shows their shortened `npub` instead of their name. **Unknown** means no connection accounts for the signature.

### What the bunker records

Besides every signature, the bunker records every change to who may sign: connection tokens issued and revoked, apps connected and disconnected, members added, removed and given another role, identity grants, the bunker relays, approvals, restores, and the log's own retention policy. Exports and pruning are recorded too. Every decrypt an app asks for is recorded before it happens.

Event content and message content are never recorded.

The page lists signatures. The other events are in the export.

### Exporting

Under **Logs**, export every signature and recorded change between two dates:

1. Choose **From** and **To**. The dates are in UTC, and both are included.
2. Choose the **Format**: **CSV** or **JSON Lines**.
3. Click **Download**.

Only administrators can export. Each export is recorded, with who made it and the range.

An exported file is outside Bancwr's control once downloaded. It holds members' and apps' public keys and names, and when they signed, but no keys that sign and no event content. Keep it as you keep your other records of who acted for the organisation.

### Retention

By default the bunker keeps everything. To keep less, open **Config**, **Log retention**, and set:

- **Keep for (days)**: delete entries older than this.
- **Keep at most (rows)**: keep only this many of the newest entries.

You can set one, or both. Each applies to signatures and to the other events separately. The shortest policy allowed is 30 days or 10,000 rows.

::warning
Saving a policy deletes what falls outside it at once. After that the bunker applies it at start and every hour. Deleted entries are gone from the database and from every backup taken afterwards, so export what you need to keep first. Earlier backups still hold them.
::

Each change of policy, and each prune that deletes anything, is recorded with what it deleted.

## The Config page

The **Config** page, titled **Bunker Configuration**, is for administrators only. It shows:

- **Current Pubkey**: the bunker's public key.
- **Key Storage**: **Encrypted at rest**, under the root credential. The private key is never shown. See [Protecting the bunker key](/docs/bancwr/protecting-the-key).
- **Identities**: the identities the bunker signs as, starting with the primary. See [Signing identities](/docs/bancwr/signing-identities).
- **Bunker relays**: the relays apps reach the bunker through. See [The connection string apps use](/docs/bancwr/urls#the-connection-string-apps-use).
- **Log retention**: see [Retention](#retention).
