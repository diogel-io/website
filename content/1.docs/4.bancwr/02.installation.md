## Overview

This page takes you from an empty server to Bancwr 0.1.0 running, with you signed in as its first administrator. Follow the steps in order. Every command runs in the directory that holds `compose.yaml`.

::note
Bancwr 0.1.0 is the first release. It is free, and published for testing and public review. Report bugs and questions as [GitHub issues](https://github.com/diogel-io/bancwr/issues). Report vulnerabilities privately, as the [security policy](https://github.com/diogel-io/bancwr/blob/v0.1.0/SECURITY.md) describes, never in a public issue.
::

## Requirements

You need:

- A Linux server you control.
- Podman with `podman compose`, or Docker with `docker compose`.
- A domain name pointing at the server, such as `bancwr.example`.
- A TLS reverse proxy in front of Bancwr, such as Caddy. Sign-in only works over HTTPS, except on `localhost`.
- `openssl`, to create the secrets.

Bancwr runs as two containers, the bunker and the console (the web dashboard). Both are released together under one version, and both run as user ID 65532, not root.

The commands below are for rootless Podman. With Docker, write `docker compose` for `podman compose` and `docker exec` for `podman exec`. Where a command differs in other ways, both are shown.

## 1. Get the compose file

Make a directory for Bancwr and download `compose.yaml` and `.env.example` from the `v0.1.0` tag:

```bash
mkdir bancwr && cd bancwr
curl -fsSLO https://raw.githubusercontent.com/diogel-io/bancwr/v0.1.0/compose.yaml
curl -fsSLO https://raw.githubusercontent.com/diogel-io/bancwr/v0.1.0/.env.example
```

`compose.yaml` pins both images to version `0.1.0`:

- `ghcr.io/diogel-io/bancwr-diogel-backend:0.1.0` (the bunker)
- `ghcr.io/diogel-io/bancwr-diogel-frontend:0.1.0` (the console)

Leave them pinned, and do not change them to `latest`: upgrading should be a change you make on purpose. See [Updating](/docs/bancwr/updating).

To check the images are the ones Bancwr's release workflow built before you run them, see [Verify the images](#verify-the-images-optional) at the end of this page.

## 2. Create the secrets

The bunker's key is encrypted at rest. Two secrets go with it, and both must exist before any `podman compose` command:

- The root credential, `secrets/bancwr_root_key`: 64 hex characters that encrypt the bunker's key.
- The backup passphrase, `secrets/bancwr_backup_key`: encrypts the bunker's backups.

Create them without either passing through your shell history:

```bash
mkdir -m 700 secrets
(umask 077; openssl rand -hex 32 > secrets/bancwr_root_key)
(umask 077; openssl rand -base64 24 > secrets/bancwr_backup_key)
```

Copy both somewhere safe now, off the server:

- Keep the root credential apart from your backups of `./data`. The encrypted key file and the root credential together are the key.
- Keep the backup passphrase apart from both the root credential and the backups. Without it, no backup can be restored.

A password manager, or an encrypted drive kept offline, will do for each. [Protecting the bunker key](/docs/bancwr/protecting-the-key) explains why they are kept apart.

## 3. Add the bunker's key for the import

The bunker signs with its own Nostr key. Every app you connect signs as this key, so make one for the bunker, and do not use your own.

Put the key, as an `nsec` or in hex, in a file. A trailing newline is fine.

```bash
(umask 077; ${EDITOR:-nano} secrets/bunker_nsec)
```

To make a new key, any Nostr key generator will do. Keep one copy of its `nsec` offline, in a password manager or on an encrypted drive. If the server is lost, that copy is the only way to keep the bunker's identity.

This file is only for the import in step 6. You delete it in step 7.

## 4. Hand the files to the bunker's user

Make the secrets read-only, create the bunker's data directory and the console's sessions directory, and give all three to user ID 65532:

```bash
chmod 400 secrets/bancwr_root_key secrets/bancwr_backup_key secrets/bunker_nsec
mkdir -p -m 700 data sessions
```

With rootless Podman:

```bash
podman unshare chown -R 65532:65532 secrets data sessions
```

With Docker:

```bash
sudo chown -R 65532:65532 secrets data sessions
```

- `./data` holds the bunker's database, `bancwr.db`, and its encrypted key file, `bunker-key.enc`.
- `./sessions` holds the console's sign-in sessions. The console refuses to start if it cannot write there.

After this step your own user can no longer read the secrets. Use `podman unshare` or `sudo` to read or replace them.

## 5. Fill in `.env`

Create `.env` from the example, readable only by you:

```bash
cp .env.example .env
chmod 600 .env
```

Then edit `.env`. The bunker's key is never set here.

### Required settings

| Variable | What it is |
|----------|------------|
| `BANCWR_ADMIN_PUBKEY` | Your own public key, as an `npub` or hex. It becomes the first administrator. It must not be the bunker's key. |
| `BANCWR_PROXY_SECRET` | A secret the console and the bunker share, so the bunker knows who is calling. |
| `NUXT_SESSION_PASSWORD` | A secret that seals the console's sign-in cookie. |
| `NUXT_SITE_ORIGIN` | The `https://` address people open Bancwr on, such as `https://bancwr.example`, with no path and no trailing slash. |

Generate `BANCWR_PROXY_SECRET` and `NUXT_SESSION_PASSWORD` separately, each with:

```bash
openssl rand -hex 32
```

Compose refuses to start without `BANCWR_PROXY_SECRET`, `NUXT_SESSION_PASSWORD` and `NUXT_SITE_ORIGIN`. `NUXT_SITE_ORIGIN` must match the address in the browser's address bar exactly. [Configuring the URLs](/docs/bancwr/urls) explains it, and the other addresses Bancwr uses.

`BANCWR_ADMIN_PUBKEY` can be left out. The first key to sign in is then told how to become the first administrator. See [First administrator and signing in](/docs/bancwr/first-administrator).

### Optional settings

Leave any of these empty or unset to use the default.

| Variable | What it does | Default |
|----------|--------------|---------|
| `NUXT_PUBLIC_PROFILE_RELAYS` | Relays the console reads and publishes members' profiles through, besides each member's own relays. Comma-separated. | damus, nos.lol and primal |
| `NUXT_PUBLIC_INDEXER_RELAYS` | Indexer relays, which collect profiles and relay lists from across the network. Comma-separated. | purplepag.es, profiles.nostr1.com and relay.nos.social |
| `NUXT_PUBLIC_BLOSSOM_SERVER` | The Blossom server profile images are uploaded to, when a member has none of their own. | blossom.primal.net |
| `NIP46_ENABLED` | Whether apps can connect to the bunker over NIP-46. Set it to `false` to turn NIP-46 off. | `true` |
| `NIP46_RELAYS` | Fixes the bunker's relays, comma-separated, such as `wss://relay.nsec.app,wss://relay.damus.io`. When set, it overrides the relays chosen in the console. | Unset: an administrator chooses them under **Config** |
| `BANCWR_APPROVAL_TIMEOUT_MINUTES` | How long a request held for an administrator's approval waits before it times out, from 1 to 1440 minutes. | 30 |

Turning NIP-46 on connects no app by itself. An administrator issues a connection token for each app. See [Connecting apps](/docs/bancwr/connecting-apps) and [Approval before signing](/docs/bancwr/approval-before-signing).

`.env.example` also lists `BUNKER_PORT`, `DATABASE_PATH`, `BANCWR_ROOT_KEY_FILE`, `BANCWR_BACKUP_KEY_FILE`, `BANCWR_KEY_PATH`, `BUNKER_NSEC_FILE` and `BUNKER_NSEC`, commented out. Leave them that way. `compose.yaml` sets the port, the paths and the secrets itself, and the bunker will not sign while `BUNKER_NSEC` or `BUNKER_NSEC_FILE` is set.

## 6. Import the key

Import the bunker's key once. This mounts the plain key for this one command only:

```bash
podman compose run --rm --no-deps \
  -v ./secrets/bunker_nsec:/run/secrets/bunker_nsec:ro,Z \
  -e BUNKER_NSEC_FILE=/run/secrets/bunker_nsec \
  bunker import-key
```

With Docker, use `docker compose` in the same command.

It encrypts the key under the root credential into `./data/bunker-key.enc` and prints the bunker's `npub`. Note the `npub`: it is the bunker's public identity.

The import never replaces an existing `./data/bunker-key.enc`. To start again, stop the bunker and remove that file first.

## 7. Delete the plain key

With rootless Podman:

```bash
podman unshare rm secrets/bunker_nsec
```

With Docker:

```bash
sudo rm secrets/bunker_nsec
```

Then check that no other plain copy is left on the server: in `.env`, in any `compose.override.yaml`, in editor backups such as `bunker_nsec~`, or in your shell history.

::warning
While `BUNKER_NSEC` or `BUNKER_NSEC_FILE` is set anywhere the bunker can see it, the bunker starts locked and signs nothing. This is on purpose: the bunker never reads a plain key while it runs. See [When the bunker will not sign](/docs/bancwr/protecting-the-key#when-the-bunker-will-not-sign).
::

## 8. Put HTTPS in front

`compose.yaml` publishes the console on `127.0.0.1:3001` only, and does not publish the bunker at all. Put a TLS reverse proxy in front of the console.

With [Caddy](https://caddyserver.com/), which obtains and renews certificates itself:

```caddy
bancwr.example {
    reverse_proxy 127.0.0.1:3001
}
```

Use the name from `NUXT_SITE_ORIGIN`. On a local network with no public name, see [The reverse proxy](/docs/bancwr/urls#the-reverse-proxy).

## 9. Start Bancwr

With Podman, make sure the Podman socket is running:

```bash
systemctl --user enable --now podman.socket
```

Start the containers:

```bash
podman compose up -d
```

## 10. Check it is running

Check the bunker's health:

```bash
podman exec bancwr-bunker bunker healthcheck
```

This asks the bunker's `/health` endpoint from inside its container, which is how compose checks it every 30 seconds. It exits without an error when the bunker is running and has unlocked its key. If the bunker is locked, it says why.

The images have no shell, so `podman exec … sh` does not work.

Check the bunker's log. Its first line carries the version, and it names the key it decrypted by its `npub`:

```bash
podman logs bancwr-bunker 2>&1 | head -n 20
```

Look for `Bancwr Diogel 0.1.0 starting...`, and check that the `npub` is the one `import-key` printed.

Check the console's version:

```bash
curl -s http://127.0.0.1:3001/api/version
```

Both should say `0.1.0`.

## 11. Sign in

Open Bancwr at your `NUXT_SITE_ORIGIN` address, such as `https://bancwr.example`. Sign in with the key you set in `BANCWR_ADMIN_PUBKEY`, through a NIP-07 browser extension such as Porwr, or a NIP-46 remote signer. [First administrator and signing in](/docs/bancwr/first-administrator) has each step.

Once you are in:

- The health indicator at the top left of every page shows the bunker's health. Until you choose the bunker's relays, its **Relays** check is red.
- The sidebar header shows the version under the name, as `V 0.1.0`.

Next:

1. Choose the bunker's relays under **Config**, **Bunker relays**. See [The connection string apps use](/docs/bancwr/urls#the-connection-string-apps-use).
2. Add your team under **Team**. See [Team and roles](/docs/bancwr/team).
3. Connect your first app under **Connections**. See [Connecting apps](/docs/bancwr/connecting-apps).
4. Set up backups. See [Backup and restore](/docs/bancwr/backup-and-restore).

## Verify the images (optional)

Release images are signed and carry signed build provenance and an SBOM, all made keyless by Bancwr's release workflow. Trunk images (`:edge`) are not signed.

Verify by digest, never by tag: a tag can move after you check it. You need [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) 3 or later and the GitHub CLI, signed in.

1. Download the release's assets for the bunker image and check them against their checksums:

   ```bash
   gh release download v0.1.0 -R diogel-io/bancwr -p 'bancwr-diogel-backend-0.1.0.*'
   sha256sum -c bancwr-diogel-backend-0.1.0.sha256
   IMAGE=$(cat bancwr-diogel-backend-0.1.0.digest)
   ```

2. Check the signature:

   ```bash
   cosign verify "$IMAGE" \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com \
     --certificate-identity-regexp '^https://github\.com/diogel-io/bancwr/\.github/workflows/release-image\.yml@refs/(heads/master|tags/v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.-]+)?)$'
   ```

3. Check the build provenance and the SBOM attestation:

   ```bash
   gh attestation verify "oci://$IMAGE" -R diogel-io/bancwr \
     --cert-oidc-issuer https://token.actions.githubusercontent.com \
     --cert-identity-regex '^https://github\.com/diogel-io/bancwr/\.github/workflows/release-image\.yml@refs/(heads/master|tags/v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.-]+)?)$'
   gh attestation verify "oci://$IMAGE" -R diogel-io/bancwr \
     --cert-oidc-issuer https://token.actions.githubusercontent.com \
     --cert-identity-regex '^https://github\.com/diogel-io/bancwr/\.github/workflows/release-image\.yml@refs/(heads/master|tags/v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.-]+)?)$' \
     --predicate-type https://spdx.dev/Document/v2.3
   ```

Repeat for `bancwr-diogel-frontend`. The identity must match exactly: a looser pattern would accept an image signed by any workflow, in any repository.

To run exactly what you verified, put the digest in `compose.yaml` in place of the tag, such as `image: ghcr.io/diogel-io/bancwr-diogel-backend@sha256:…`. A pinned digest does not get the weekly base-image rebuilds, so verify and pin the new digest after each one. See [Weekly rebuilds](/docs/bancwr/updating#weekly-rebuilds).

Compose does not check signatures. Verifying is your step.
