## Image tags

The bunker and the console share one version and are released together. Each image is published with several tags.

| Tag | Points at |
|-----|-----------|
| `latest` | The newest release. Written only by a release. |
| `<version>`, such as `0.1.0` | That release. |
| `<major>.<minor>`, such as `0.1` | The newest patch of that release line. |
| `edge` | Trunk: the latest merged code, not a reviewed release. |
| `master` | The same image as `edge`. |
| `<semVer>`, such as `0.1.1-3` | One trunk build, by its version. |
| `sha-<short>` | One specific commit. |

- `latest` only moves forward, to the highest stable release. A patch to an older line, such as `0.1.5` after `0.2.0`, leaves `latest` alone. There is no `:0` style tag for a major version.
- Trunk is `edge`, never `latest`. Use `edge` only to try what has merged but not been released. Trunk images are not signed.

The [releases page](https://github.com/diogel-io/bancwr/releases) is the record of what has been released.

### Weekly rebuilds

Every Monday at 05:00 UTC, the newest release and trunk are rebuilt on fresh base images. Each rebuild runs the same tests and vulnerability scan before it is published, and is signed in the same way.

A rebuilt release keeps its version and its code. Only the image digest changes. This brings base-image security fixes to what you run within a week, without a new release.

If you pin an image by digest, you do not get these fixes until you verify and pin the new digest. See [Verify the images](/docs/bancwr/installation#verify-the-images-optional).

### How versions are set

Each release's version is set by its release pull request. [release-please](https://github.com/googleapis/release-please) reads the changes merged since the last release and works out the next version. Merging that pull request creates the `v<version>` tag, and the images are built from it. Both images always get the same version.

Trunk builds are versioned separately, from the latest release tag, such as `0.1.1-3`.

## Choosing a tag

`compose.yaml` pins an exact version for both images, such as `0.1.0`. Upgrading is then a deliberate change to that file.

Always use the same version for both images.

## How to update

1. Read the release notes on the [releases page](https://github.com/diogel-io/bancwr/releases) for anything you need to do.
2. Take a backup. See [Backup and restore](/docs/bancwr/backup-and-restore).
3. Edit the two `image:` lines in `compose.yaml` to the new version, for both the bunker and the console. Or download the new release's `compose.yaml` and compare it with yours.
4. Pull the new images:

   ```bash
   podman pull ghcr.io/diogel-io/bancwr-diogel-backend:0.1.0
   podman pull ghcr.io/diogel-io/bancwr-diogel-frontend:0.1.0
   ```

5. Recreate the containers:

   ```bash
   podman compose up -d
   ```

Replace `0.1.0` with the version you are updating to.

Your data is kept in `./data`, and sign-in sessions in `./sessions`, so both survive the update. Nobody is signed out.

To pick up a weekly rebuild of the version you already run, pull the same tag again and recreate the containers.

## Checking the running version

After updating, check that both parts run the new version.

- **In the console:** the sidebar header shows the version under the name, such as `V 0.1.0`.
- **The console container:**

  ```bash
  curl -s http://127.0.0.1:3001/api/version
  ```

- **The bunker container:** its first log line carries its version, such as `Bancwr Diogel 0.1.0 starting...`.

  ```bash
  podman logs bancwr-bunker 2>&1 | grep -m1 'starting'
  ```

If the versions differ, the two containers were not updated together. Check both `image:` lines in `compose.yaml`.

## Upgrading from an early build to 0.1.0

Before 0.1.0, only trunk builds were published, as `:edge` or a version such as `0.1.0-99`. Those builds read the bunker's key in plain text, from `BUNKER_NSEC` in `.env` or from the file `BUNKER_NSEC_FILE` names.

0.1.0 keeps the key encrypted at rest, and never reads a plain key. After upgrading, the bunker does not sign until the key is imported and every plain copy is removed. Until then it runs locked and says so.

Upgrade in this order. The commands are for rootless Podman. With Docker, use `docker compose`, `docker exec` and `sudo` where shown.

1. Take a cold copy of `./data`, as [A cold copy of `./data`](/docs/bancwr/backup-and-restore#a-cold-copy-of-data) shows. A build that reads a plain key cannot run `bunker backup`. The copy may hold the key in plain text, so keep it as carefully as the key, and delete it once 0.1.0 is running.

2. Stop the bunker:

   ```bash
   podman compose stop bunker
   ```

3. Put the bunker's key in a file for the import. If it is in `.env` as `BUNKER_NSEC`:

   ```bash
   mkdir -p -m 700 secrets
   (umask 077; ${EDITOR:-nano} secrets/bunker_nsec)
   chmod 400 secrets/bunker_nsec
   ```

   Paste the value of `BUNKER_NSEC` from `.env`, save and close. If you already used a secret file, it is `secrets/bunker_nsec` already.

4. Create the root credential and the backup passphrase, and copy both somewhere safe off the server:

   ```bash
   (umask 077; openssl rand -hex 32 > secrets/bancwr_root_key)
   (umask 077; openssl rand -base64 24 > secrets/bancwr_backup_key)
   chmod 400 secrets/bancwr_root_key secrets/bancwr_backup_key
   ```

5. Create the sessions directory, and hand the secrets, the data and the sessions to user ID 65532. Early builds ran as root, so `./data` may belong to root.

   ```bash
   mkdir -p -m 700 sessions

   # Rootless Podman
   podman unshare chown -R 65532:65532 secrets data sessions

   # Docker
   sudo chown -R 65532:65532 secrets data sessions
   ```

6. Replace `compose.yaml` with the one from the `v0.1.0` tag:

   ```bash
   curl -fsSLO https://raw.githubusercontent.com/diogel-io/bancwr/v0.1.0/compose.yaml
   ```

   It no longer passes `BUNKER_NSEC`, and it mounts `./secrets/bancwr_root_key` and `./secrets/bancwr_backup_key` as secrets. If you have a `compose.override.yaml`, remove its `:edge` image lines, its `BUNKER_NSEC_FILE` line and its `bunker_nsec` secret, or delete the file if that leaves nothing.

7. Check `.env` against the [v0.1.0 `.env.example`](https://github.com/diogel-io/bancwr/blob/v0.1.0/.env.example). See [Fill in `.env`](/docs/bancwr/installation#_5-fill-in-env) for each setting.

8. Import the key, as in [Import the key](/docs/bancwr/installation#_6-import-the-key):

   ```bash
   podman compose run --rm --no-deps \
     -v ./secrets/bunker_nsec:/run/secrets/bunker_nsec:ro,Z \
     -e BUNKER_NSEC_FILE=/run/secrets/bunker_nsec \
     bunker import-key
   ```

   Check that the `npub` it prints is the bunker's `npub` from before.

9. Remove every plain copy: delete `secrets/bunker_nsec` as in [Delete the plain key](/docs/bancwr/installation#_7-delete-the-plain-key), delete the `BUNKER_NSEC` line from `.env`, and delete any other copy of `.env` that still holds it.

10. Pull the images, start Bancwr, and check it is healthy and has the same `npub`:

    ```bash
    podman pull ghcr.io/diogel-io/bancwr-diogel-backend:0.1.0
    podman pull ghcr.io/diogel-io/bancwr-diogel-frontend:0.1.0
    podman compose up -d
    podman exec bancwr-bunker bunker healthcheck
    podman logs bancwr-bunker 2>&1 | grep 'Public key'
    ```

    If the health check says the plain key is still configured, step 6 or 9 left `BUNKER_NSEC` or `BUNKER_NSEC_FILE` set somewhere. Find it with:

    ```bash
    podman inspect bancwr-bunker --format '{{range .Config.Env}}{{println .}}{{end}}' | grep NSEC
    ```

11. Take your first encrypted backup. See [Backup and restore](/docs/bancwr/backup-and-restore).

::warning
The key was in plain text on this server before. Encrypting it now does not undo any copy already made, in a backup of `.env` or of the server. Nostr has no way to rotate or revoke a key, so if such a copy may have left your control, treat the key as exposed.
::

### What else changes from an early build

- **Roles.** Members move from Administrator, User and Signer to Admin, Signer and Viewer at the first start. The old Signer becomes Viewer and loses their app connections. See [Upgrading from an early build](/docs/bancwr/team#upgrading-from-an-early-build) on the Team page.
- **Sessions.** Everyone signs in once more after this upgrade. From then on, restarting or upgrading the console keeps everyone signed in.
- **Rate limits.** Apps connected before the upgrade keep working, limited to the default of 60 signing and encryption requests a minute, with a burst of 20. An app that needs more needs a new token with a higher limit.
- **Old backups.** Builds before the key was kept out of the database could store the `nsec` in plain text in its `config` table. Current builds delete it at start, but a copy of `./data` made before then still holds it. Treat such a copy as a copy of the key, or delete it.
